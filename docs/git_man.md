# Описание работы с системой контроля версий **Git**

---

Здесь описываются базовые команды для работы с удалённым репозиторием, а также команды для работы с нативными средствами git в локальном формате.

> Для нашего проекта будет целесообразно иметь возможность работать с системой патчей

---

## Базовое использование

После создания чистого репозитория или при отсутствии связи с удалённым репозиторием необходимо зафиксировать его командой:

```bash
git remote add origin https://github.com/{логин гитхаба}/vu_backend.git
```

Далее нужно переименовать ветку для сервиса:

```bash
git branch -M main
```

А после работаем стандартно...

---

### Сценарии использования средств **git** в разработке

Сначала нужно взять за основу единый подход к разработке. В данном случае грамотной реализацией будет работа с ветками.

> Подход заключается в том, что в проекте "чистый" код хранится итоговой веткой `main` или `release` (второе по ходу разработки можно создать для релизных версий).
> 
> У каждого человека должна быть своя соответствующая задача в проекте, которая реализуется в отдельной ветке. Ветки принято называть `feature/{и краткое название функционала, который реализуется в ветке}`.
> 
> Каждый коммит в ветке так и пушится в удалённый репозиторий (если ветка не была создана удалённо ранее, то эту новую `origin` ветку нужно указывать при пуше).
> 
> После окончания реализации средствами GitHub необходимо создать Pull Request для визуализации изменений и слияния ветки в `main` отдельным коммитом и соответствующей историей в репозитории.
> 
> При новой подзадаче цикл с созданием ветки, работой в ней и слиянии повторяется.

---

### Команды для работы с проектом

- **Определить удалённый репозиторий в локальном проекте:**
  ```bash
  git remote add origin https://github.com/DenisKut/vu_backend.git
  ```
  > Таким образом `origin` — это удалённый репозиторий

- **Клонировать репозиторий:**
  ```bash
  git clone https://github.com/DenisKut/vu_backend.git
  ```

- **Создать новую ветку:**
  ```bash
  git branch {название ветки (лучше в формате: feature/*название фичи*)}
  ```

- **Посмотреть список веток:**
  ```bash
  git branch -l
  ```

- **Переключиться на ветку:**
  ```bash
  git checkout {название ветки}
  ```

- **Создать и сразу переключиться в новую ветку:**
  ```bash
  git checkout -b {название ветки}
  ```

- **Загрузить изменения из текущей ветви в origin в нужную ветвь:**
  ```bash
  git push origin feature
  ```

## Небольшая сноска из статьи

> Когда ваш pull request примут, не забудьте слить изменения в свой репозиторий (или удалить его, если больше не нужен):

```bash
git checkout master
git pull upstream master
git push origin master
```

> Также можно удалить ветку, в которой велась разработка:

```bash
git branch -d feature # В локальном репозитории
git push origin :feature # В удалённом репозитории
```

> Что делать, если работа заняла много времени и оригинальный репозиторий ушёл вперёд?
> Можно просто влить изменения из оригинального репозитория к себе:

```bash
git checkout master
git pull upstream master
git checkout feature
git merge master
```

> Однако хозяину оригинального репозитория или вам могут не понравиться merge-коммиты и коммиты из master'а в списке коммитов на pull request. В таком случае используйте git rebase:

```bash
git checkout master
git pull upstream master
git checkout feature
git rebase master # Всё отличие только здесь
```

## Наш подход к работе

1. Клонируем репозиторий.
2. Ветки создаются по фамилиям участников.
3. При реализованном функционале пушим в одноимённые удалённые ветки (и локально, и удалённо).
4. После завершения feature создаём pull request на GitHub с данной реализацией в основную ветку `main`.
5. Не удаляем ветку ни удалённо, ни локально (только при подходе создания отдельной ветки под функциональность, поскольку в этой ветке могут работать все поочерёдно).

## При работе с патчами

### 1. Создание патчей

- **Из последних коммитов:**
  ```bash
  # Создать патчи для последних N коммитов
git format-patch HEAD~3  # Патчи для 3 последних коммитов
  ```
  ```bash
  # Создать патчи всех коммитов, которых нет в main
git format-patch main -o patches/
  ```

- **Из конкретной ветки:**
  ```bash
  # Создать патчи всех коммитов ветки `feature`, которых нет в `main`
git format-patch main..feature
  ```

- **Из незакоммиченных изменений:**
  ```bash
  # Создать патч из текущих изменений (включая unstaged)
git diff > my-changes.patch
  ```

- **Создание патча между ветками:**
  ```bash
  git diff main..feature > feature-changes.patch
  ```

---

### 2. Применение патчей

- **С сохранением истории коммитов (`git am`)**
  Используется для патчей, созданных через git format-patch:
  ```bash
  # Применить все патчи из текущей директории
git am *.patch

# Применить конкретный патч
git am 0001-fix-bug.patch
  ```

- **Проверка патча перед применением:**
  ```bash
  git apply --check my-changes.patch  # Проверить, нет ли конфликтов
  ```
  > **Важно:** Патчи применяются как отдельные коммиты с сохранением автора, даты и сообщения.

- **Без сохранения истории (`git apply`)**
  Если нужно применить изменения как обычный diff (без коммитов):
  ```bash
  git apply my-changes.patch
  ```

---

### 3. Решение конфликтов

Если при применении патча возникают конфликты:

1. Git остановит процесс и сообщит о проблеме.
2. Вручную разрешите конфликты в файлах.
3. Продолжите применение патча:
   ```bash
   git am --continue
   ```
   или отмените:
   ```bash
   git am --abort
   ```
4. Для сложных случаев используйте `--3way`:
   ```bash
   git am --3way *.patch  # Попытается автоматически разрешить конфликты
   ```
5. Патчи и бинарные файлы:
   - Git плохо работает с бинарными файлами в патчах, поэтому:
     ```bash
     git diff --binary > changes.patch  # Включить бинарные файлы
     ```

---

### 4. Инструменты просмотра репозитория локально

- **GitK (Windows):**
  ```bash
  gitk --all
  ```
  _Плюсы:_ Простой, показывает историю и ветки.  
  _Минусы:_ Устаревший интерфейс.

- **Gitg (Linux):**
  _Установка:_
  ```bash
  sudo apt install gitg  # Ubuntu/Debian
  ```
  _Плюсы:_ Интеграция с GNOME, поддержка тегов и веток.  
  _Минусы:_ Только для Linux.

- **Веб-интерфейс Ungit:**
  _Установка:_
  ```bash
  npm install -g ungit
  ```
  _Запуск:_
  ```bash
  ungit --port=8080  # Открыть http://localhost:8080
  ```
  _Плюсы:_ Интерактивный, подходит для новичков.  
  _Минусы:_ Требует Node.js.

## Полная инструкция по работе с `git stash`

`git stash` — команда в Git, позволяющая временно сохранить изменения в рабочем каталоге и индексе (staging area), чтобы переключиться на другую ветку или выполнить другие действия, не теряя текущих изменений. Это полезно, если вы хотите отложить текущую работу, не создавая коммит.

### 1. Сохранение изменений

- **Сохранить все изменения (включая неиндексированные):**
  ```bash
  git stash
  ```

- **Сохранить только индексированные изменения:**
  ```bash
  git stash --keep-index
  ```

- **Сохранить изменения с сообщением:**
  ```bash
  git stash push -m "Описание изменений"
  ```

- **Сохранить только изменения в конкретном файле:**
  ```bash
  git stash push -m "Описание изменений" -- <путь_к_файлу>
  ```

---

### 2. Просмотр сохранённых изменений

- **Список всех сохранённых изменений:**
  ```bash
  git stash list
  ```
  Пример вывода:
  ```
  stash@{0}: On main: Исправление ошибки
  stash@{1}: WIP on feature: Добавление новой функции
  ```

---

### 3. Применение изменений

- **Применить последний `stash`:**
  ```bash
  git stash apply
  ```

- **Применить конкретный `stash`:**
  ```bash
  git stash apply stash@{1}
  ```

- **Применить изменения и удалить `stash`:**
  ```bash
  git stash pop
  ```

---

### 4. Удаление сохранённых изменений

- **Удалить последний `stash`:**
  ```bash
  git stash drop
  ```

- **Удалить конкретный `stash`:**
  ```bash
  git stash drop stash@{1}
  ```

- **Удалить все `stash`:**
  ```bash
  git stash clear
  ```

---

### 5. Создание патча из `stash`

- **Создать патч из последнего `stash`:**
  ```bash
  git stash show -p > my-stash.patch
  ```

---

### 6. Применение изменений в новой ветке

- **Создать ветку из `stash`:**
  ```bash
  git stash branch <имя_ветки>
  ```

---

### 7. Просмотр содержимого `stash`

- **Посмотреть изменения в последнем `stash`:**
  ```bash
  git stash show
  ```

- **Посмотреть изменения в конкретном `stash`:**
  ```bash
  git stash show stash@{1}
  ```

- **Посмотреть полный дифф изменений:**
  ```bash
  git stash show -p
  ```

---

### Пример использования

1. Вы работаете над новой функцией, но нужно срочно переключиться на другую ветку:
   ```bash
   git stash push -m "Работа над новой функцией"
   git checkout main
   ```
2. После завершения работы на другой ветке, вернитесь к изменениям:
   ```bash
   git checkout feature
   git stash apply
   ```
3. Если изменения больше не нужны, удалите их:
   ```bash
   git stash drop
   ```
