# Описание работы с системой контроля версий **Git**

---

Здесь описываются базовые команды для работы с удалённым репозиторием, а также команды для работы с нативными средствами git в локальном формате.

> Для нашего проекта будет целесообразно иметь возможность работать с системой патчей

---

## Базовое использование

После создания чистого репозитория или при отсутствии связи с удалённым репозиторием необходимо зафиксировать его командой:

```bash
git remote add origin https://github.com/{логин гитхаба}/vu_backend.git
```

Далее нужно переименовать ветку для сервиса:

```bash
git branch -M main
```

А после работаем стандартно...

---

### Сценарии использования средств **git** в разработке

Сначала нужно взять за основу единый подход к разработке. В данном случае грамотной реализацией будет работа с ветками.

> Подход заключается в том, что в проекте "чистый" код хранится итоговой веткой `main` или `release` (второе по ходу разработки можно создать для релизных версий).
> 
> У каждого человека должна быть своя соответствующая задача в проекте, которая реализуется в отдельной ветке. Ветки принято называть `feature/{и краткое название функционала, который реализуется в ветке}`.
> 
> Каждый коммит в ветке так и пушится в удалённый репозиторий (если ветка не была создана удалённо ранее, то эту новую `origin` ветку нужно указывать при пуше).
> 
> После окончания реализации средствами GitHub необходимо создать Pull Request для визуализации изменений и слияния ветки в `main` отдельным коммитом и соответствующей историей в репозитории.
> 
> При новой подзадаче цикл с созданием ветки, работой в ней и слиянии повторяется.

---

### Команды для работы с проектом

- **Определить удалённый репозиторий в локальном проекте:**
  ```bash
  git remote add origin https://github.com/DenisKut/vu_backend.git
  ```
  > Таким образом `origin` — это удалённый репозиторий

- **Клонировать репозиторий:**
  ```bash
  git clone https://github.com/DenisKut/vu_backend.git
  ```

- **Создать новую ветку:**
  ```bash
  git branch {название ветки (лучше в формате: feature/*название фичи*)}
  ```

- **Посмотреть список веток:**
  ```bash
  git branch -l
  ```

- **Переключиться на ветку:**
  ```bash
  git checkout {название ветки}
  ```

- **Создать и сразу переключиться в новую ветку:**
  ```bash
  git checkout -b {название ветки}
  ```

- **Загрузить изменения из текущей ветви в origin в нужную ветвь:**
  ```bash
  git push origin feature
  ```

## Небольшая сноска из статьи

> Когда ваш pull request примут, не забудьте слить изменения в свой репозиторий (или удалить его, если больше не нужен):

```bash
git checkout master
git pull upstream master
git push origin master
```

> Также можно удалить ветку, в которой велась разработка:

```bash
git branch -d feature # В локальном репозитории
git push origin :feature # В удалённом репозитории
```

> Что делать, если работа заняла много времени и оригинальный репозиторий ушёл вперёд?
> Можно просто влить изменения из оригинального репозитория к себе:

```bash
git checkout master
git pull upstream master
git checkout feature
git merge master
```

> Однако хозяину оригинального репозитория или вам могут не понравиться merge-коммиты и коммиты из master'а в списке коммитов на pull request. В таком случае используйте git rebase:

```bash
git checkout master
git pull upstream master
git checkout feature
git rebase master # Всё отличие только здесь
```

## Наш подход к работе

1. Клонируем репозиторий.
2. Ветки создаются по фамилиям участников.
3. При реализованном функционале пушим в одноимённые удалённые ветки (и локально, и удалённо).
4. После завершения feature создаём pull request на GitHub с данной реализацией в основную ветку `main`.
5. Не удаляем ветку ни удалённо, ни локально (только при подходе создания отдельной ветки под функциональность, поскольку в этой ветке могут работать все поочерёдно).

## Работа с патчами в Git

Патчи позволяют переносить изменения между репозиториями, ветками или рабочими директориями. Это удобно для обмена изменениями, ревью, резервного копирования или применения изменений вручную.

---

### 1. Что такое патч и как он выглядит

Патч — это текстовый файл, содержащий разницу (diff) между двумя состояниями репозитория. Он может включать изменения в коде, структуре файлов, а также метаданные (автор, дата, сообщение коммита — если патч создан через `git format-patch`).

- **Обычный diff-патч** (через `git diff`) содержит только изменения в файлах.
- **Патч через `git format-patch`** содержит всю информацию о коммите: автора, дату, сообщение, diff, и может применяться с сохранением истории.
- **Патчи могут быть в текстовом или бинарном формате** (флаг `--binary`).

---

### 2. Создание патчей

#### 2.1. Патч для неиндексированных изменений (unstaged)
```bash
git diff > changes.patch
```
_Сохраняет все изменения, которые ещё не были добавлены в индекс (`git add`)._

#### 2.2. Патч для индексированных изменений (staged)
```bash
git diff --cached > staged_changes.patch
```
_Сохраняет только изменения, которые были добавлены в индекс, но ещё не закоммичены._

#### 2.3. Патч для всех текущих изменений (staged + unstaged)
```bash
git diff HEAD > all_changes.patch
```
_Включает все изменения относительно последнего коммита._

#### 2.4. Патч между двумя коммитами
```bash
git diff <commit1_hash>..<commit2_hash> > commit_range.patch
```
_Сохраняет разницу между двумя коммитами. Можно использовать сокращённые или полные хэши, теги, ветки._

#### 2.5. Патч для одного коммита
```bash
git show <commit_hash> > single_commit.patch
# или
git diff <commit_hash>^! > single_commit.patch
```
_`^!` означает "разница между коммитом и его родителем"._

#### 2.6. Патч для всей ветки (от точки расхождения с другой веткой)
```bash
git diff main..feature_branch > branch_diff.patch
```
_Сравнивает ветку `feature_branch` с `main` и сохраняет разницу._

#### 2.7. Патч с бинарными файлами
```bash
git diff --binary > binary_changes.patch
```
_Включает изменения бинарных файлов (например, изображений)._

#### 2.8. Формирование патча через `git format-patch`

`git format-patch` создаёт один или несколько файлов в формате email, которые содержат всю информацию о коммитах (автор, дата, сообщение, diff). Такой патч можно отправить по почте или применить с сохранением истории через `git am`.

- **Патч для одного коммита:**
  ```bash
  git format-patch -1 <commit_hash>
  ```
- **Патчи для всех коммитов, которых нет в другой ветке:**
  ```bash
  git format-patch main..feature
  ```
- **Патчи для последних N коммитов:**
  ```bash
  git format-patch -N
  # Например, для 3 последних коммитов:
  git format-patch -3
  ```
- **Сохранить патчи в отдельную папку:**
  ```bash
  git format-patch main..feature -o patches/
  ```

**Флаги format-patch:**
- `-o <dir>` — сохранить патчи в указанную директорию
- `-k` — не перекодировать сообщения коммитов
- `--cover-letter` — создать отдельный файл с сопроводительным письмом
- `--subject-prefix` — добавить префикс к теме письма

**Особенности:**
- Каждый патч — отдельный файл с расширением `.patch` или `.eml`.
- Внутри содержится информация о коммите, diff, авторе, дате, теме и теле сообщения.
- Можно применять по одному или все сразу (`git am *.patch`).

---

### 2.9. Создание патча, объединяющего несколько коммитов в один файл

Иногда нужно создать один патч, который содержит изменения сразу из нескольких коммитов (например, для отправки большого блока изменений одним файлом). Для этого используйте диапазон коммитов с помощью двойной точки (`..`) или `HEAD~N`:

- **Патч для диапазона коммитов (например, последних 3):**
  ```bash
  git diff <старший_коммит> <младший_коммит> > multi_commit.patch
  # Например, для последних 3 коммитов:
  git diff HEAD~3 HEAD > multi_commit.patch
  ```
  _Включает все изменения между указанными коммитами в один файл._

- **Патч для всех коммитов ветки, которых нет в другой ветке:**
  ```bash
  git diff main..feature > feature_all.patch
  ```
  _Всё отличие ветки feature от main в одном патче._

- **Объединить несколько коммитов в один патч через format-patch и cat:**
  ```bash
  git format-patch -3
  cat 0001-*.patch 0002-*.patch 0003-*.patch > all_in_one.patch
  ```
  _Объединяет несколько файлов-патчей в один (может быть полезно для пересылки или применения одним файлом)._ 

**Совет:**
- Для чистого объединения изменений лучше использовать `git diff`, так как `git format-patch` всегда создаёт отдельный файл на каждый коммит.

---

### 3. Применение патчей

#### 3.1. Применение diff-патча без создания коммита (`git apply`)
```bash
git apply changes.patch
```
_Вносит изменения в рабочую директорию, но не создаёт коммит._

- **Проверить патч перед применением:**
  ```bash
  git apply --check changes.patch
  ```
- **Попробовать автоматическое разрешение конфликтов:**
  ```bash
  git apply --3way changes.patch
  ```
- **Флаги:**
  - `--stat` — показать, какие файлы изменятся
  - `--reverse` — отменить изменения, внесённые патчем

#### 3.2. Применение патча с созданием коммита и сохранением истории (`git am`)
```bash
git am 0001-some-change.patch
```
_Применяет патч, созданный через `git format-patch`, и создаёт коммит с сохранением автора, даты и сообщения._

- **Применить все патчи из папки:**
  ```bash
  git am patches/*.patch
  ```
- **Флаги:**
  - `--signoff` — добавить подпись к коммиту
  - `--3way` — использовать трёхстороннее слияние при конфликте
  - `--skip` — пропустить проблемный патч
  - `--abort` — отменить применение патчей

---

### 4. Разрешение конфликтов при применении патчей

Если при применении патча возникли конфликты:

1. **Git сообщит о конфликте и остановит процесс.**
2. Откройте конфликтующие файлы (ищите строки с `<<<<<<<`, `=======`, `>>>>>>>`).
3. Вручную исправьте конфликт, оставив нужные изменения.
4. Добавьте исправленные файлы:
   ```bash
   git add resolved_file.txt
   ```
5. Продолжите применение патча:
   - Для `git am`:
     ```bash
     git am --continue
     ```
   - Для `git apply`:
     _Просто закоммитьте изменения вручную:_
     ```bash
     git commit -m "Resolve patch conflict"
     ```
6. Если нужно отменить применение патча:
   ```bash
   git am --abort
   ```

---

### 5. Советы, особенности и типичные ошибки

- **Патчи не всегда хорошо работают с бинарными файлами.** Используйте опцию `--binary` или передавайте такие файлы отдельным архивом.
- **Проверяйте патч перед применением** с помощью `git apply --check`.
- **Для сложных случаев используйте трёхстороннее слияние**: `git apply --3way` или `git am --3way`.
- **Патчи, созданные через `git format-patch`, лучше применять через `git am`** — так сохраняется история коммитов.
- **Следите за порядком применения патчей**: если патчи зависят друг от друга, применяйте их в том же порядке, в каком они были созданы.
- **Патчи чувствительны к контексту**: если код сильно изменился после создания патча, возможны конфликты.
- **Используйте короткие или полные хэши коммитов** — оба варианта работают, но полные хэши надёжнее.
- **Патчи можно просматривать и редактировать вручную** — это обычные текстовые файлы.

---

### 6. Примеры типовых сценариев

#### 6.1. Создать патч для последних 3 коммитов и отправить коллеге
```bash
git format-patch HEAD~3
# Получатся файлы вида 0001-..., 0002-..., 0003-...
```

#### 6.2. Применить патч и проверить, нет ли конфликтов
```bash
git apply --check changes.patch
git apply changes.patch
```

#### 6.3. Создать патч между ветками и применить его
```bash
git diff main..feature > feature.patch
git checkout main
git apply feature.patch
```

#### 6.4. Применить серию патчей с сохранением истории
```bash
git am patches/*.patch
```

#### 6.5. Создать патч для одного коммита по его хэшу
```bash
git format-patch -1 <commit_hash>
# или
git show <commit_hash> > single_commit.patch
```

#### 6.6. Применить патч с трёхсторонним слиянием
```bash
git am --3way 0001-some-change.patch
```

## Работа с временным сохранением изменений (`git stash`)

`git stash` позволяет временно сохранить (отложить) все или часть изменений в рабочем каталоге и индексе, чтобы переключиться на другую ветку или выполнить другие действия, не теряя текущей работы. Это особенно полезно, если нужно срочно заняться другой задачей, не делая лишних коммитов.

---

### 1. Сохранение изменений

- **Сохранить все изменения (включая неиндексированные):**
  ```bash
  git stash
  ```
  _Сохраняет все изменения в рабочем каталоге и индексе._

- **Сохранить только индексированные изменения:**
  ```bash
  git stash --keep-index
  ```
  _Сохраняет только те изменения, которые были добавлены в индекс (`git add`)._

- **Сохранить изменения с комментарием:**
  ```bash
  git stash push -m "Описание изменений"
  ```
  _Позволяет добавить пояснение к сохранённым изменениям._

- **Сохранить изменения только в определённом файле:**
  ```bash
  git stash push -m "Описание" -- путь/к/файлу
  ```

---

### 2. Просмотр и управление сохранёнными изменениями

- **Посмотреть список всех stash:**
  ```bash
  git stash list
  ```
  _Показывает все сохранённые состояния с их номерами (stash@{0}, stash@{1}, ...)._ 

- **Посмотреть изменения в stash:**
  ```bash
  git stash show stash@{0}
  git stash show -p stash@{0}  # Полный diff
  ```

- **Удалить последний stash:**
  ```bash
  git stash drop
  ```
- **Удалить конкретный stash:**
  ```bash
  git stash drop stash@{1}
  ```
- **Удалить все stash:**
  ```bash
  git stash clear
  ```

---

### 3. Применение и восстановление изменений

- **Применить последний stash (оставить в списке):**
  ```bash
  git stash apply
  ```
- **Применить конкретный stash:**
  ```bash
  git stash apply stash@{1}
  ```
- **Применить stash и удалить его из списка:**
  ```bash
  git stash pop
  ```
- **Создать новую ветку из stash:**
  ```bash
  git stash branch <имя_ветки>
  ```
  _Автоматически создаёт ветку и применяет к ней изменения._

---

### 4. Создание патча из stash

- **Сделать патч из stash:**
  ```bash
  git stash show -p > my-stash.patch
  ```
  _Можно отправить этот патч или применить его вручную через `git apply`._

---

### 5. Советы и особенности

- Можно иметь несколько stash — они хранятся в стеке, последний всегда под номером 0.
- Старайтесь давать осмысленные комментарии при сохранении (`-m`), чтобы не запутаться.
- Если изменения не нужны — удаляйте stash, чтобы не захламлять стек.
- Stash не сохраняет новые неотслеживаемые файлы (но можно с флагом `-u`):
  ```bash
  git stash -u  # Сохранить и неотслеживаемые файлы
  ```

## Графические и веб-интерфейсы для просмотра истории и веток

Для удобного анализа истории коммитов, веток и слияний можно использовать различные инструменты:

### 1. Gitk (кроссплатформенный)
- **Запуск:**
  ```bash
  gitk --all
  ```
- **Возможности:**
  - Просмотр истории коммитов, веток, тегов
  - Визуализация слияний и разветвлений
  - Поиск по сообщениям коммитов и авторам
- **Плюсы:** Простота, не требует отдельной установки (часто входит в git).
- **Минусы:** Устаревший интерфейс, мало настроек.

### 2. Gitg (Linux)
- **Установка (Ubuntu/Debian):**
  ```bash
  sudo apt install gitg
  ```
- **Возможности:**
  - Графический просмотр истории, веток, тегов
  - Просмотр изменений в файлах
  - Интеграция с GNOME
- **Плюсы:** Удобен для пользователей Linux, поддержка drag-and-drop.
- **Минусы:** Только для Linux.

### 3. Ungit (веб-интерфейс)
- **Установка:**
  ```bash
  npm install -g ungit
  ```
- **Запуск:**
  ```bash
  ungit --port=8080
  # Открыть http://localhost:8080 в браузере
  ```
- **Возможности:**
  - Визуальное отображение веток, коммитов, слияний
  - Интерактивное управление (merge, rebase, reset, push, pull)
  - Просмотр diff, история изменений
- **Плюсы:** Современно, удобно для новичков, работает в браузере.
- **Минусы:** Требует установленного Node.js.

### 4. Дополнительные инструменты
- **GitKraken, SourceTree, GitHub Desktop** — кроссплатформенные клиенты с расширенными возможностями визуализации, управления ветками, разрешения конфликтов и интеграции с сервисами.
- **Встроенные средства IDE (VS Code, PyCharm и др.)** — позволяют просматривать историю, ветки, diff, выполнять базовые git-операции прямо из редактора.
